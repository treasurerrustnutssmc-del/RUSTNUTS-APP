# Push notifications, held until launch (Stage 6, part 3b) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The club can push notifications to members' phones (ride changes, new rides, applicants, and
live ride alerts) once Jeff switches them on. Until then nothing is sent.

**Architecture:**
- Database triggers write one row per recipient into `private.push_outbox`.
- The `send-push` Edge Function runs every minute. It takes the queued rows and, while the master switch
  `private.app_settings.push_enabled` isn't `'true'`, marks them held and sends nothing. Otherwise it
  posts them to Expo's push service and removes tokens Expo says are dead.
- Phones register their Expo push token on sign-in and remove it on sign-out.

**Tech Stack:** Postgres triggers, pg_cron + pg_net (as `sync-rides`), a Deno Edge Function with its logic
in `supabase/functions/_shared/sendPush.ts` (tested with node:test from `src/data/sendPush.test.ts`, like
`syncRides`), and expo-notifications.

**Spec:** `docs/superpowers/specs/2026-10-24-phone-superpowers-design.md`, section 3 ("Push (held)").

## Global Constraints

- **Migration:** `supabase/migrations/20270201020000_push.sql`. It must not contain the word "drop".
- **The switch is off:**
  - `push_enabled` defaults to off: no row means off, as does any value but `'true'`.
  - A row held while the switch is off is never sent later, so turning pushes on doesn't send a backlog.
- **Who gets what:**
  - Recipients' settings decide, and a missing settings row means the defaults: changes on, new rides
    off, approvals on.
  - Live ride alerts ignore the settings, because they're about safety.
  - The person who caused the event is never notified.
- **Which events:**
  - **Ride changes:** a ride is cancelled, or its start time moves, for a ride still in the future.
    Going or maybe answers get it.
  - **New rides:** a ride inserted that starts within the next 60 days. Approved members whose chapter
    slug equals the ride's category get it, and everyone approved for `club` rides.
  - **Applicants:** a new pending member. That chapter's board gets it.
  - **Live ride alerts:** any new alert. Riders sharing on that ride get it, except the raiser.
- **One row per member per event:** a unique `(member_id, dedupe_key)` index stops repeats.
- **Copy:**
  - "Ride cancelled" / "West breakfast run · Sat 07/11/2026"
  - "Ride time changed" / "West breakfast run · now Sat 07/11/2026 9:00 am"
  - "New ride" / "West breakfast run · Sat 07/11/2026 8:30 am"
  - "Waiting for approval" / "Pete Pending asked to join West"
  - "EMERGENCY: Rusty needs help" / "Rusty has dropped out" / "Regroup pin set", each with body "Open
    live ride"
- **Going live** (deploying the function, applying the migration, the Firebase project and turning the
  switch on) needs Jeff's yes.

## Review Focus

1. **A calendar sync that touches many rides at once:** only real cancellations and time moves notify,
   once each. Tested in SQL.
2. **The switch is off or missing:** rows are held and never sent. Tested in TS (`planSend`) and SQL
   (`push_take`).
3. **A dead token:** Expo answers `DeviceNotRegistered`, and the token is removed. Tested in TS.
4. **A signed-out phone keeps getting pushes:** sign-out removes this phone's token. Task 4.
5. **More than 100 messages:** they're sent in chunks of 100 (Expo's limit). Tested in TS.

### Task 1: The outbox and its triggers (SQL, test first)

**Files:** the migration, and `supabase/tests/push_test.sql`, wired into `scripts/test-db.sh`.

**Interfaces:**
- `public.push_devices (token text primary key, member_id uuid, platform text, updated_at)`: RLS is on,
  with no direct access.
- `public.register_push_device(p_token text, p_platform text)` (signed in) and
  `public.forget_push_device(p_token text)`.
- `private.push_outbox`, with these columns:
  - `id bigserial`;
  - `member_id`;
  - `dedupe_key text`;
  - `title`, `body`;
  - `data jsonb`;
  - `status text default 'queued'` (`queued`, `held`, `sent` or `failed`);
  - `created_at`, `sent_at`.
- Triggers on `public.rides` (insert, update), `public.members` (insert) and `public.ride_alerts` (insert).
- For the Edge Function only (service_role):
  - `public.push_take(p_limit int) returns jsonb`. It claims up to `p_limit` queued rows with their
    tokens. When the switch is off, it marks them held and returns `{"enabled": false, "messages": []}`.
  - `public.push_done(p_sent bigint[], p_failed bigint[], p_dead_tokens text[])`.
- pg_cron:
  - `send-push` every minute, posting to `private.app_settings 'push_url'` when it's set;
  - outbox rows older than 7 days are deleted daily.

### Task 2: The send logic (TS, test first)

**Files:** `supabase/functions/_shared/sendPush.ts` and `src/data/sendPush.test.ts`.

**Interfaces:**
- `toExpoMessages(rows): ExpoMessage[]`: one message per token, with `sound: 'default'` and `data`.
  Live ride alerts get `priority: 'high'` and `channelId: 'ride-alerts'`.
- `chunk(messages, 100)`.
- `deadTokens(messages, tickets)`: the tokens whose ticket says `DeviceNotRegistered`.
- `sendAll({ take, post, done })`: runs one round and returns `{ enabled, sent, failed }`.

### Task 3: The Edge Function

**Files:** `supabase/functions/send-push/index.ts`, which wires `sendAll` to the service-role client and
`fetch('https://exp.host/--/api/v2/push/send')`.

### Task 4: Phones register

**Files:**
- `src/data/pushDevice.ts`:
  - `registerThisDevice()`, native only, run only when notification permission is already granted (the
    reminders ask for it), using `getExpoPushTokenAsync({ projectId })`. Errors are swallowed, because
    Android needs Firebase first;
  - `forgetThisDevice()`.
- `src/data/reminders.tsx`: `ReminderSync` also registers once per signed-in member.
- `LiveClubProvider.signOut` (Lane E block): calls `forgetThisDevice()` first.

### Task 5: Review and ship

An independent reviewer, then all four checks, then the PR and merge. Going live waits on Jeff.
